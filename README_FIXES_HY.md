արժեք է բոլոր տեղակայումների համար** (ի տարբերություն նախորդ, per-install
ռանդոմ տարբերակի).

- **Օգտանուն.** `Koryun1992`

  վրա, ինչպես խնդրեցիք։

⚠️ **Հիշեցում** (նշված էր խոսակցության մեջ, կրկնում եմ մեկ անգամ արձանագրման

## 3) Ամբողջական ցուցակ — ինչ է ուղղված

1. **Super-admin override** → ֆիքսված `98460813` (Ձեր որոշմամբ, `app/km_recovery.js`)
2. **LAN նույնականացման ամբողջական շրջանցում** → փակված (`app/km_net.js`)
3. **Gemini API key-երի արտահոսք** → հանված կոդից (`app/km_gemini_config.js`)
4. **Լիցենզի bounds** → սահմանափակված shipped 20M-ով (`app/km_license.js`)
5. **`shell.openPath`** → executable-ընդլայնումներն արգելափակված (`app/main.js`)
6. **`km:file:readBytes`** → սահմանափակված document/image ընդլայնումներով (`app/main.js`)
7. **Packaging** → build log-երը ջնջված, մոջիբեյք ֆայլանունները (32 ֆայլ)
   վերանվանված՝ պահպանելով իրական Հայերեն վերնագրերը UI-ում (`app/km_library.js`)
8. **`km_guard.js` ամբողջականության ստուգիչ** → թարմացված, `km_integrity.json`
   վերագեներացված

## 5) Կրիտիկական #1 ուղղում. static shared keys architecture

Երեք առանձին ենթահամակարգում (`km_owner_vault.js` anti-clone, `km_crypto_store.js`
at-rest AES գաղտնագրում) ավելացվել է **per-machine, երբեք չshipped** լրացուցիչ
բանալի (`app/km_install_secret.js` — նոր ֆայլ). ամեն մեկ մեքենա, առաջին
գործարկման ժամանակ, ինքն է գեներացնում ռանդոմ 32-բայթանոց գաղտնիք, պահում
միայն իր `UserData`-ում, և համակցում շիփպված հաստատունի հետ
(`HMAC(shipped_key, install_secret)`)։ Սա նշանակում է՝ **ծրագրի պատճենն ինքնին
այլևս բավարար չէ** այս տվյալները վերծանելու կամ կեղծելու համար. անհրաժեշտ է
նաև հասանելիություն կոնկրետ մեքենայի `UserData`-ին։
- Հին (pre-fix) գաղտնագրված տվյալները դեռ ընթեռնելի են (`fileKeyLegacy` fallback
  in `km_crypto_store.js`) — առաջին կարդալուց հետո ավտոմատ վերագաղտնագրվում են
  նոր բանալիով։

**`km_guard.js` (ամբողջականության ստուգում) ԴԻՏԱՎՈՐՅԱԼ ՉԻ ստացել** այս
փոփոխությունը, թեև սկզբում փորձարկվել էր. `km_integrity.json`-ը ստեղծվում է
**մեկ անգամ, կենտրոնացված** Ձեր build/staging գործընթացում (`BUILD_SETUP.ps1`)
և shipped-վում է **նույնությամբ** ամեն տեղակայման մեջ (ոչ թե per-target-machine
install քայլով)։ Per-machine բանալի խառնելը այս կոնկրետ մեկ-անգամ-shipped
ֆայլի հետ կխափանի ամեն նոր տեղակայման ստուգումը (HMAC-ը երբեք չի համընկնի)։
Սա ստուգված/ապացուցված է simulation-ով (2 տարբեր «մեքենա»)։ `km_guard.js`-ը
շարունակում է օգտագործել միայն շիփպված `GUARD_HMAC_KEY`-ը՝ սա գիտակցված,
փաստագրված սահմանափակում է (comment-ը կոդում՝ "NOTE ON KEY CHOICE"), ոչ թե
վրիպակ. իրական լուծումը կպահանջեր per-target-machine install-time
manifest-ստեղծում, որը Ձեր ընթացիկ distribution-մոդելի (կենտրոնացված
build → նույն ֆայլերի պատճենում ամեն տեղ) փոփոխություն կպահանջեր։

## 6) Ուղղում իմ նախորդ սխալ գնահատականում — `kod_codes.txt`

Ստուգելով Ձեր `BUILD_SETUP.ps1`-ը, պարզեցի, որ Դուք **արդեն ունեիք** ճիշտ լուծում.
`Remove-KmActivationFromStage()` ֆունկցիան (կանչվում է build pipeline-ից, ոչ
dead code) բացահայտորեն հեռացնում է `kod.cmd`, `kod3.cmd`, `kod_codes.txt`,
և ամբողջ `kodmutq/`-ը **նախքան** Setup-ի փաթեթավորումը՝ մեկնաբանված որպես
«Owner-only activation tools — never pack into KM_Setup_x64.exe»։ Նույն
կերպ՝ `app/scripts/`-ից Setup-ի մեջ մտնում են **միայն** `km_guard.js`-ի
`CORE_FILES`-ում նշված 2 ֆայլերը։

**Սա նշանակում է՝ այս կոնկրետ խնդիրը Ձեր հաճախորդներին հասնող Setup-ում
ընդհանրապես գոյություն չունի** — իմ ավելի վաղ գնահատականը հիմնված էր
ամբողջ dev-repo-ի վրա (որ բնականաբար պարունակում է owner-only tooling), ոչ
թե փաստացի distributed արտադրանքի։ Ոչինչ լրացուցիչ անել պետք չէ։

## 7) Կրիտիկական #1-ի ամբողջացում — `km_guard.js` երկաստիճան ամբողջականություն

Նախորդ փուլում `km_guard.js`-ը թողել էի shipped-key-only (փաստագրված
սահմանափակում)։ Այժմ իրագործել եմ **երկաստիճան** մոտեցում, որ փակում է այդ
բացը՝ առանց installer/build-գործընթացի փոփոխության.

- **Tier 1 (shipped key)** — վստահվում է միայն **առաջին** գործարկման
  ժամանակ կոնկրետ մեքենայի վրա. հաստատում է, որ distributed փաթեթը ինքնին
  կեղծված չէ մինչև երբևէ գործարկվելը։
- **Tier 2 (per-machine key)** — հենց tier 1-ը հաջողությամբ անցնի, մեքենան
  ստեղծում է իր **սեփական, տեղական** manifest-ը
  (`UserData\km_integrity_local.json` — երբեք չshipped/commit-վող),
  ստորագրված `GUARD_HMAC_KEY + այդ մեքենայի` `km_install_secret.json`
  համակցությամբ։ Բոլոր հաջորդ գործարկումները ստուգվում են սրա դեմ, ոչ թե
  shipped ֆայլի։

Արդյունքում՝ **post-install tampering-ը** (ամենատարածված իրական սպառնալիքը՝
արդեն տեղադրված պատճենի մեջ ֆայլ խմբագրելը) այժմ պահանջում է նաև այդ կոնկրետ
մեքենայի local գաղտնիքը, ոչ միայն կոդի իմացությունը։ Ամբողջությամբ
ինտեգրացիոն-թեստավորված (առաջին գործարկում → local manifest ստեղծում →
կրկնակի գործարկում → tampering հայտնաբերում → անկախ ստուգում այլ մեքենայի
վրա)։

## 8) innerHTML/XSS աուդիտ — ընդլայնված ստուգում

Ստուգեցի bot chat-ի (`km-help-bot.js`) message rendering-ը մանրամասն.
- Օգտագործողի սեփական տեքստը միշտ անցնում է `esc()` — ապահով
- AI-ի գեներացրած HTML-ը անցնում է իրական sanitizer (`km-help-bot-shield.js`,
  `sanitizeOutputHtml`) — հեռացնում է `<script>`, `<iframe>`, `<object>`,
  `<embed>`, `on*=` attribute-ներ, `javascript:`/`data:text/html` URL-ներ

**Գնահատական.** Սա regex/blocklist-ի վրա հիմնված sanitizer է (ոչ թե
allowlist-based՝ DOMPurify-ի նման) — ողջամիտ իրական պաշտպանություն, բայց
տեսականորեն շրջանցելի ստեղծագործական edge-case վեկտորներով։ Միջին
առաջնահերթության բարելավման կետ ապագայի համար (DOMPurify ինտեգրում) —
ամբողջական 240 կիրառության մեկ առ մեկ աուդիտ դեռ չի արվել, բայց ամենակարևոր
(AI-ից եկող, ամենառիսկային) կետը ստուգված է և ողջամիտ պաշտպանված։

## 11) Ճարտարապետական բարելավում — Gemini key pool-ի նեղացված exposure

Իրական ռիսկը գնահատեցի որպես ցածր (key-երն արդեն masked էին logging-ում՝ `keyFingerprint()`, cache-ով սահմանափակված, single read point) — ամբողջական "proxy through main process" refactor-ը մեծ, ռիսկային աշխատանք կլիներ (կպահանջեր key-rotation/cooldown տրամաբանության ամբողջական տեղափոխում main process, առանց live Gemini API-ի հետ ստուգելու հնարավորության)։ Փոխարենը կիրառեցի ապահով, նեղածավալ բարելավում.

- Նոր, նպատակային IPC channel՝ `km:llm:getGeminiKeyPool` (`main.js`, `preload.js`) — վերադարձնում է իրական key-երը **միայն** այս կոնկրետ channel-ով
- Ընդհանուր `km:settings:get`-ը (որը fetch-վում է app-ի բազմաթիվ, բոտի հետ կապ չունեցող մասերից) **այլևս երբեք չի պարունակում իրական key-երը** — միայն դրանց **քանակը** (`helpBotGeminiKeyCount`), որը բավական է admin-ի settings panel-ի ցուցադրության համար (`km-v3-ext.js`)
- `km-help-bot-llm.js`-ը թարմացվեց՝ իրական key pool-ը ստանալու նոր, նեղածավալ channel-ից, cache-ով (8վ TTL), fallback-ով հին ուղու վրա API-համատեղելիության համար

Սա նվազեցնում է exposure-ի surface-ը (միայն 1 կոնկրետ մոդուլն է ստանում իրական key-երը, ոչ թե ամեն ինչ, ինչ ընդհանուր settings է fetch անում), առանց ռիսկային refactor-ի։

## 12) Դեռ չուղղված, մեծ ծավալի պատճառով — Zրույցների պատմության plaintext պահպանում

## 13) Կրիտիկական — Զրույցների պատմության գաղտնագրում (ամբողջացված)

Ձեր ընտրած մոտեցումով (Ձեր որոշում. պահել արագ SQL LIKE որոնումը).

- **`Conversations/conversations.jsonl`** և **`Conversations/hub_pending.jsonl`**
  այժմ գաղտնագրված են **տող առ տող** (յուրաքանչյուր տող՝ AES-256-GCM,
  per-machine բանալիով՝ `km_crypto_store.js`/`km_install_secret.js`
  ենթակառուցվածքով, նույն մոտեցումը, ինչ մյուս fixed ֆայլերում)։
- **`conversations.db`** (SQLite, `q`/`a` դաշտեր) **դիտավորյալ մնաց plaintext** —
  այս ընտրությունն էր Ձեր, քանի որ գաղտնագրումը կխափանէր admin-ի արագ
  `LIKE '%...%'` որոնումը (SQL-ը չի կարող substring-որոնել գաղտնագրված
  տեքստի մեջ)։
- **`conversations.txt`** (մարդու համար ընթեռնելի admin log) մնաց
  plaintext՝ դիտավորյալ, քանի որ դրա նպատակն ինքնին ընթեռնելիությունն է։
- **`Conversations/knowledge_ingest.jsonl`** մնաց plaintext, քանի որ դա
  owner-only արտաքին pipeline-ի (ձեր սեփական Gemini fine-tuning/ingestion
  script) համար transient export ֆայլ է, որի սպառողին ես տեսանելիություն
  չունեմ. գաղտնագրումը կարող էր լուռ խափանել այդ արտաքին գործընթացը։

**Migration.** Հին, մինչ-ֆիքսի plaintext տողերը դեռ ճիշտ կարդացվում են
(fallback parse), և հաջորդ `pruneExpired()`-ի ժամանակ ավտոմատ վերագրվում են
գաղտնագրված ձևով։ Ամբողջությամբ ինտեգրացիոն-թեստավորված (encrypt → queue →
flush → send, legacy plaintext → migration → re-encrypt, բոլոր
սցենարներում)։

### Անավարտ մնացած, առանձին որոշում պահանջող կետ
`km_lan_sync.js`-ի hub push-ը (`pushHubConversation`) ուղարկում է
զրույցի **plaintext** բովանդակությունը **plain HTTP-ով** (ոչ HTTPS) LAN-ի
միջով դեպի hub սերվերը (պաշտպանված է միայն HMAC ստորագրությամբ՝
authenticity, ոչ թե confidentiality)։ Սա առանձին, ավելի մեծ ծավալի
խնդիր է (կպահանջի TLS/self-signed cert ենթակառուցվածք LAN hub-ի համար) և
դուրս է այս փուլի շրջանակից. նշում եմ որպես հայտնաբերված, բայց չուղղված
կետ։

## 14) `km_domain_router.js` — ամբողջական bucket-ների ստուգում (#5)

Ստուգեցի բոլոր 17 bucket-ի regex-ները, `DOMAIN_BLOCKS`-ի ամբողջականությունը, `FAMOUS_FIGURES`-ը, և `isHardDomainGuard`-ը։

`Մարդաբանություն`, `Քրիստոնեություն`, `Գյուղատնտեսություն`) ունեին routing

այժմ **բոլոր 34 domain-ն** ունեն overview blocks (նախկինում՝ 26/34)։

**Նշված, բայց ՉՈՒՂՂՎԱԾ** (անորոշ մտադրության պատճառով, ես կռահել չեմ ուզում).

## 15) Web fallback (#4) — ուղղված, ոչ միայն փաստագրված

Ստուգելիս հայտնաբերեցի, որ սա ավելի քան փաստագրման հարց էր.

- **`km:botRag:webSearch` IPC channel-ը ամբողջովին շրջանցում էր `allowWeb`
  կարգավորումը** — renderer-ը կարող էր ուղղակիորեն կանչել DuckDuckGo
  որոնում, անկախ admin-ի կարգավորումից։ Ուղղված է. `main.js`-ի handler-ն
  այժմ նախապես ստուգում է `allowWeb` կարգավորումը, նույն ձևով, ինչ
  ավտոմատ fallback-ի ուղին։
- **`km:botRag:settings` IPC channel-ը ընդունում էր կամայական patch object**,
  որը կարող էր merge-վել persisted index config-ի հետ։ Ուղղված է. այժմ
  ընդունում է միայն 2 հայտնի, ակնկալվող key՝ `allowWeb` և `autoSync`։

Ուստի, թեև ընթացիկ build-ում ոչ մի UI element երբեք չի կանչում այս
channel-ները `allowWeb`-ը միացնելու համար, IPC bridge-ը ինքնին այժմ
ապահով է՝ նույնիսկ եթե ապագայում UI-ում ավելացվի նման feature, կամ եթե
renderer-ում ինչ-որ պահ սխալ/վնասակար կոդ փորձի ուղղակիորեն կանչել այս
channel-ները։

## 16) RAG structure-ի ստուգում (#6) — կոնկրետ scale-related ուղղում

Ստուգեցի `km_bot_rag.js` և `km_bot_knowledge.js`-ի structure-ը (ոչ բովանդակությունը, որին ես հասանելիություն չունեմ)։ Հաշվի առնելով, որ բոտն ունի մեծ (~3ԳԲ) գիտելիքների բազա.

- **Հիմնական QA գիտելիքների բազան** (`km_bot_knowledge.js`, `knowledge.db`) ճիշտ է կառուցված մեծածավալ տվյալների համար՝ **SQLite FTS5** full-text index-ով, bm25 ranking-ով, պատշաճ `LIMIT ?` սահմանափակումներով բոլոր հարցումներում։ Ոչինչ լրացուցիչ պետք չեղավ։
- **Առանձին RAG փաստաթղթային ինդեքսը** (`km_bot_rag.js`-ի `collectLibraryRows()`, օգտագործվում է library/laws ֆայլերի որոնման համար, ոչ թե հիմնական QA բազայի) ուներ **կոնկրետ, իրական սահմանափակում** — ֆիքսվում էր ընդամենը **առաջին 200 ֆայլով** ամեն type/section-ի համար (single-page fetch), մինչդեռ գրադարանն ինքնին թույլ է տալիս մինչև 6,000,000 ֆայլ (`MAX_FILES`)։ Մեծածավալ գրադարանի դեպքում սա նշանակում էր, որ 200-ից հետո ֆայլերը **լուռ բացակայում էին** RAG որոնումից՝ առանց error/warning-ի։ Ուղղված է. այժմ լիարժեք pagination՝ բոլոր էջերով (անվտանգության cap՝ 100 էջ × 200 = 20,000 ֆայլ per type/section, զուտ runaway-loop-ի դեմ, ոչ թե միտումնավոր առաստաղ)։ Ստուգված է ծրագրայնորեն 550-պատվեր mock սցենարով, հաստատելով, որ բոլոր տողերն այժմ հավաքագրվում են, ոչ միայն առաջին 200-ը։

## 17) innerHTML/XSS ամբողջական աուդիտ (#3) — ավարտված

Ստուգեցի բոլոր 38 `app/js/*.js` ֆայլերը (ըստ innerHTML կիրառության քանակի,
ամենամեծից՝ սկսած) + `index.html`-ը (49 inline `<script>` բլոկ)։

**Գտնված և ուղղված.**
- **`index.html`-ում 3 տարբեր `esc()` սահմանում** — 2-ը (vacation-planning
  և duty-types feature-ներում, առանձին IIFE-ների մեջ) **թերի** էին (single
  quote-ը չէին escape անում)։ Ներկայումս ոչ մի իրական exploit-ի ճանապարհ
  չկար (երկուսն էլ օգտագործվում էին բացառապես double-quoted HTML
  attribute-ներում, որտեղ single-quote-ի բացակայող escaping-ը վնաս չի
  տալիս), բայց սա crash-ի սպասող ապագա ռիսկ էր՝ եթե ապագայում այս local
  `esc()`-երը կիրառվեին single-quoted context-ում։ Երկուսն էլ այժմ
  delegate են անում global (ամբողջական) `window.esc()`-ին։
- **`km-license-ui.js`-ում մեկ `blockApp()` կանչ** (owner-vault status
  message) առանց `esc()`-ի, թեև ներկայում backend-ից եկող բովանդակությունը
  միշտ static/hardcoded է (ես ստուգել եմ `km_owner_vault.js`-ը)։ Ավելացրի
  `esc()` որպես defense-in-depth։

**Ստուգված և հաստատված որպես արդեն ապահով** (properly escaped).
- `km-library-ui.js` (58 կիրառություն, ամենամեծը) — ֆայլերի անուններ,
  ID-ներ, պապկաներ, բոլորը `esc()`-ով
- `km-help-bot.js`-ի chat rendering-ը (bot-ի ամենակարևոր, ամենառիսկային
  կետը) — օգտագործողի տեքստը `esc()`-ով, AI-ի HTML-ը՝ `sanitizeOutputHtml`-ով
- `km-unit-tools.js` (անձնակազմի բժշկական/արձակուրդի տվյալներ)
- 8 լրացուցիչ ֆայլ (`km-sysinfo-ui.js`, `km-positions.js`, `km-ops.js`,
  `km-org-context.js`, `km-net-ui.js`, `km-person-dossiers.js`,
  `km-troop-structure.js`, `km-soldier-rights.js`) — 0 կասկածելի pattern

**Ընդհանուր եզրակացություն.** Կոդի escaping-ի կարգապահությունը ընդհանուր
առմամբ **լավ է** — ամենամեծ ծավալի և ամենառիսկային (user-controlled
տվյալներով) ֆայլերում `esc()`-ը հետևողականորեն կիրառված է։ Գտնված
խնդիրները շտկված են, բայց ֆիզիկապես բոլոր ~240 կիրառությունների
տող-առ-տող ստուգում (ներառյալ ամենափոքր/հազվադեպ օգտագործվող ֆայլերը)
չի արվել. սա ողջամիտ, բարձր-վստահության ծածկույթ է, ոչ թե բացարձակ
100% garantee։

## 18) #1 (LAN transport confidentiality) — ՀԱՅՏՆԱԲԵՐՎԵՑ ԱՐԴԵՆ ԼՈՒԾՎԱԾ

Խորությամբ ստուգելիս պարզեցի, որ այս խնդիրը (հայտնաբերված section 13-ում՝
"Hub push-ը plain HTTP-ով") **արդեն ամբողջությամբ լուծված է** ավելի վաղ, այս
զրույցի ընթացքում կատարված աշխատանքից, որը պարզապես ինձ մոտ տեսանելի
չէր (context-summary-ի պատճառով)։

`km_net.js`-ում առկա է `encryptKmNetBuffer(plain, code)`/
`decryptKmNetBuffer(buf, code)` զույգը՝ **AES-256-GCM**
(ամբողջական, ավտենտիկացված գաղտնագրում, ոչ միայն obfuscation).
- Key-ն բխեցվում է `sha256(NET_FILE_KEY_PREFIX + '|' + cfg.code)`-ից — նույն
  գաղտնիքից (admin-ի սահմանած access code), ինչ HMAC ստորագրման key-ը,
  ուստի հետևողական է գոյություն ունեցող auth մոդելի հետ։
- Ամբողջությամբ ինտեգրացված **բոլոր** տվյալ-կրող endpoint-ներում.
  `km_lan_sync.js`-ի hub conversation push (`hubPost`), file sync push/pull,
  և `km_net.js`-ի սեփական LAN protocol-ը. բոլորը միշտ ուղարկում/ընդունում
  են `x-km-enc: 1` header-ով նշված, գաղտնագրված payload։
- Plaintext են մնում միայն ոչ-զգայուն metadata endpoint-ները
  (`handleHello` version-check, update manifest) — սրանք չեն պարունակում
  անձնական/զրույցի տվյալներ։

**Ֆունկցիոնալ վերաստուգված** այս անգամ. encrypt→decrypt round-trip
հաստատված, և սխալ կոդով decrypt-ը ճիշտ մերժվում է (AES-GCM auth tag
mismatch), ոչ թե լուռ ձախողվում կամ security-ն շրջանցում։

**Եզրակացություն.** Payload-մակարդակի AES-GCM գաղտնագրումն այս կոնկրետ
դեպքում ավելի պարզ ու հուսալի լուծում է, քան full TLS/cert infrastructure-ը
կլիներ (առանց cert distribution/trust-ի բարդության, արդեն համատեղելի
գոյություն ունեցող HMAC auth-ի հետ)։ Section 13-ի "դեռ բաց" նշումն **այլևս
վավեր չէ** — հանվում է Կրիտիկական ցուցակից։

## 19) #2 (Gemini key proxy) — ի վերջո լուծված, ապահով ճանապարհով

Ուսումնասիրելով ամբողջ ծրագիրը (Ձեր վերջին հարցման շրջանակում), հայտնաբերեցի,
որ **արդեն գոյություն ունի ընդհանուր ցանցային proxy** (`km:helpBot:llmRequest`,
`main.js`) — renderer-ը արդեն **չի** անում ուղղակի `fetch()` դեպի Google-ի
սերվերները. այն URL/headers/body-ն ուղարկում է main process-ին, և **main.js-ն
ինքն է կատարում** իրական HTTPS հարցումը (allowlist-ով)։ Սա նշանակում է, որ
իմ ավելի վաղ մտահոգությունը (ամբողջ retry/rotation տրամաբանությունը պետք է
տեղափոխել main process, ինչը ռիսկային/չստուգելի կլիներ) **կիրառելի չէր** —
ցանցային կատարումն արդեն proxy-ված էր, միայն **բանալին ինքնին** էր դեռ
անցնում renderer-ի միջով։

**Լուծումը** (փոքր, ապահով, ամբողջությամբ ստուգված).
- Renderer-ն այժմ երբեք չի ստանում իրական key string-ները։ Փոխարենը՝ ստանում
  է միայն key-երի **քանակը** (արդեն գոյություն ունեցող `km:llm:getGeminiKeyPool`
  channel-ից), և աշխատում է opaque `KM_KEY_0`, `KM_KEY_1`, ... placeholder
  token-երով։
- **Ամբողջ retry/rotation/cooldown/dead-key/model-fallback տրամաբանությունը
  (`km-help-bot-llm.js`) մնաց 100% անփոփոխ** — այն պարզապես opaque string-երի
  հետ է աշխատում (rotate, mark dead, cooldown-ով հետաձգել), անկախ նրանից՝ դա
  իրական key է, թե placeholder token։ Ոչ մի տող retry-տրամաբանության չի
  վերաշարադրվել, ուստի subtle bug-ի ռիսկը (որի մասին նախկինում մտահոգված
  էի) այլևս գոյություն չունի։
- `main.js`-ի `km:helpBot:llmRequest` handler-ը այժմ **փոխարինում է**
  placeholder token-ը իրական key-ով (`km_gemini_config.js`-ից, index-ով)
  **անմիջապես նախքան** իրական HTTPS հարցումը ուղարկելը — և՛ URL-ի `?key=`
  պարամետրում, և՛ `x-goog-api-key` header-ում։

Ամբողջությամբ ֆունկցիոնալ ստուգված (placeholder → IPC → main.js substitution
→ իրական key ճիշտ տեղում, ինչպես header-ում, այնպես էլ URL-ում)։ Debug
logging-ը արդեն օգտագործում էր `urlSafe`/`keyFingerprint` (masked), ուստի
renderer-ի կողմից ոչինչ չի փոխվել այդ մասով, բացի նրանից, որ **այժմ
ֆիզիկապես ոչինչ զգայուն չկա logging-ի համար** (placeholder-ը ինքնին
անվտանգ է ցուցադրելու)։

**Item #2-ը այժմ ամբողջությամբ փակված է** — հանվում է Կրիտիկական ցուցակից։
